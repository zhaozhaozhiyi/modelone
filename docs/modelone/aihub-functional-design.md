# AIHub 功能设计

> 本设计以仓库保留的上游产品说明为需求来源，面向自建 AIHub 的场景。AIHub 是独立产品模块：自己的页面、业务 API、应用版本和调用记录；与现有平台只共享登录、用户、项目空间、数据库和反向代理基础设施。这里同时区分首期已开发的能力和后续目标，不把旧模型市场目录视为已发布应用。

## 1. 产品定位

AIHub 是模型应用市场和在线体验层，提供三项核心能力：

1. 模型应用市场：浏览、搜索、分类和查看模型应用。
2. 在线体验：在浏览器中填写输入并查看模型输出。
3. API：为已接入的模型应用提供统一、可鉴权、可追踪的调用接口。

AIHub 不负责 Notebook 开发、模型微调、推理服务创建或 Kubernetes 调度。模型应用的运行端点由管理员预先配置或由其他平台服务提供，AIHub 只负责登记、展示、体验和转发调用。用户入口为独立的 `/aihub/` 页面，业务接口统一使用 `/aihub/api/`，不嵌入通用资源卡片页。

## 2. 上游需求与开源现状

上游说明同时提出了模型应用 SDK、Web/API 体验、预训练模型目录、一键 Notebook 开发、一键微调、一键部署、Label Studio 对接和 Pipeline 算子注册。本项目只采用其中的模型市场、Web 体验和 API 能力；其余能力明确排除在 AIHub 范围之外。详见[上游功能清单](../upstream/README.md)和[上游项目简介](wiki/项目简介.md)。

| 能力 | 当前仓库情况 | 设计处理 |
| --- | --- | --- |
| 分类市场和卡片列表 | 有 `Aihub` 元数据表、分类列表 API 和通用卡片页 | 保留现有路由，补应用详情、筛选和可用状态 |
| 模型应用规范与 SDK | 仓库有 YOLOv8 示例，但其引用的 `cubestudio.aihub` SDK 不在当前 `aihub/` 目录中 | 只定义满足市场、体验和 API 的应用清单与运行协议 |
| Web 体验和推理 API | 当前卡片的开发、训练、部署链接是占位链接 | 改为详情、体验和 API 调用入口 |
| 运行端点 | 平台已有推理服务能力，但 AIHub 没有统一应用端点协议 | 接入管理员预配置的运行端点，不在 AIHub 内创建服务 |
| 一键开发、微调和部署 | 上游有描述，当前需求明确不纳入 AIHub | 不设计入口、数据模型或编排流程 |
| Label Studio 与 Pipeline 复用 | 上游文档提出了对接目标 | 不纳入当前 AIHub 范围；需要时由独立模块调用 API |
| 400+预训练模型 | 种子 JSON 是目录元数据，不是完整模型包 | 只接入自行选择且许可、权重、镜像均可核验的应用 |

当前 `init-aihub.json` 有 502 条记录，501 条满足导入器的基本字段要求；其中 474 条会显示“请联系管理员开通”，495 条镜像值为占位符 `xx`。这些数字不能视为已交付的可运行模型数量。

## 3. 功能设计

### 3.1 模型应用市场

- 按机器视觉、语音、自然语言、多模态和大模型浏览；未归类条目进入“其他”。
- 支持按任务场景、输入类型、框架、标签、发布状态和资源需求筛选，支持名称和描述搜索。
- 列表展示名称、任务、摘要、版本和分类；详情页可切换概览、在线体验和 API。
- 首期详情展示模型来源与许可、应用版本、输入输出 Schema 和运行端点状态；示例、文档与资源说明在 P1 补齐。
- 对每项应用明确标记“可体验”和“API 可用”，不展示开发、微调或部署入口。
- 市场只展示已发布的应用。端点临时故障时保留卡片与详情，标出不可用状态；调用接口在健康或修订校验失败时拒绝转发。

### 3.2 在线体验与推理 API

- 首期根据 JSON Schema 渲染文本、数字和布尔输入，展示结构化 JSON 结果。图片、音频、视频、文件与产物下载属于后续协议扩展。
- 首期支持同步请求；耗时较长的应用在 P1 使用异步运行记录，提供排队、运行、成功、失败状态和结果查询。
- 为每个已发布版本提供稳定的 API 路径、请求示例、错误格式、鉴权方式和健康状态。
- 在线体验调用已配置的运行端点，不创建新服务、不修改副本数、不触发模型部署。
- 首期 API 使用已有的限时平台 API 令牌和项目成员关系；不宣称已提供独立 API 密钥。专用密钥的签发、轮换、撤销和配额在后续版本另行设计，运行端点凭据只以服务端环境变量引用保存。
- 首期记录调用耗时、状态和错误类型，不保存请求主体、原始文件或敏感输入；去标识化摘要需单独评估后再加入。

### 3.3 应用接入与发布

- 首期由平台管理员登记应用元数据、输入输出 JSON Schema、端点地址、端点修订和可见范围；开发者自助接入在 P2 开放。
- 创建时校验字段、JSON Schema 和项目空间，得到草稿版本；发布时再检查端点元数据与健康状态。代码、镜像、依赖和许可的自动化审核在 P2 补齐。
- 发布后版本不可原地覆盖；新代码、新权重或运行环境变更都创建新版本。
- 首期状态为“草稿 → 已发布 → 已下架”，发布校验同步执行。P1 增加校验中、已弃用和变更说明工作流。

### 3.4 管理、权限和运行治理

- 首期由平台管理员维护应用目录、可见范围、发布状态和运行端点。项目成员可以访问项目可见应用；项目管理员的细粒度授权在 P1 引入。
- 应用可设为平台公开、项目可见或仅创建者可见；模型权重、运行端点凭据和内部地址不随目录公开。
- 首期发布记录模型来源、许可、可选权重摘要和端点修订；模型代码与镜像摘要核验在 P2 补齐。
- 首期记录调用者、版本、耗时、状态和错误类型，不记录输入正文；P1 增加聚合指标、配额和限流，不做商业计费。

## 4. 应用包与运行协议

每个应用版本由发布后不可修改的应用清单和运行端点绑定组成。模型文件、容器镜像和 Kubernetes 服务由运行端点所属系统负责，AIHub 只保存必要的来源和校验信息。清单至少描述：

| 字段组 | 内容 |
| --- | --- |
| 身份 | 首期：应用 ID、版本、名称、分类、任务、创建者；P1：文档和变更说明 |
| 来源与许可 | 代码来源、模型来源、代码许可、权重许可、权重校验值 |
| 运行环境 | 首期：运行端点地址、修订和固定健康协议，内部地址与凭据不公开；P1：兼容性和资源说明 |
| 推理界面 | 首期：输入输出 JSON Schema 与同步 JSON 协议；P1：文件类型、示例和异步能力 |
| 体验与 API | 首期：Schema 驱动输入、版本路径和平台令牌；P1：体验配置与更多协议 |

首期运行端点协议固定为：`GET {base}/metadata` 返回 `application_id`、`version`、`revision`；`GET {base}/health` 返回 `{"status":"ok"}`；`POST {base}/predict` 接收 `{"inputs":{...}}`，返回 `{"result":...}`。`inputs` 与 `result` 分别按发布的 JSON Schema 校验。发布和每次调用都要核对元数据中的三项身份，健康检查失败时拒绝调用，避免同一版本路径在端点被替换后悄然改变结果。首期请求体上限 1 MiB、响应体上限 2 MiB、推理超时 30 秒；失败以 HTTP 状态和 `{"error":{"code":"...","message":"..."}}` 返回。文本生成的流式、OpenAI 兼容协议与异步任务在 P1 扩展。

浏览器和外部客户端分别使用平台会话和限时平台 API 令牌。AIHub 不转发调用者的 Cookie/Authorization；如端点需要凭据，管理员填服务端环境变量名，令牌值不入库、不进入公开清单。AIHub Web 进程不导入或执行应用 Python 代码，也不创建或升级 Kubernetes 服务。
运行端点主机必须列入服务端 `AIHUB_ENDPOINT_HOSTS` 允许列表；默认空列表拒绝接入。首期禁止回环、链路本地等地址，后续接入平台内推理服务时应优先使用稳定的服务标识与网络隔离。

旧 `/model_market/*/api` 路由和 `Aihub` 表只承担历史兼容，不作为新页面数据源，也不自动迁移为已发布版本。新目录使用 `aihub_application_version` 表，以 `(slug, version)` 唯一约束保存独立版本；管理员创建草稿并校验端点后发布。旧初始化命令可继续更新历史目录，但不能修改新表中的已发布版本。列表、详情、健康检查与推理调用都按公开、项目成员、创建者三种可见性在服务端过滤；浏览权限不等于管理权限。

## 5. 逻辑流程

```mermaid
flowchart LR
  Dev[提交应用清单和运行端点] --> Check[校验与发布]
  Check --> Catalog[AIHub 市场与详情]
  Catalog --> Demo[Web 体验/API 调用]
  Demo --> Endpoint[已配置的模型运行端点]
  Endpoint --> Result[体验结果与 API 响应]
```

## 6. 实施顺序

### P0：跑通一个应用

- 完成独立页面、应用清单、详情页、发布状态和运行端点绑定；不沿用通用卡片页。
- 选择一个许可清楚、已有稳定运行端点的模型应用。
- 跑通 Web 输入、推理结果、API 调用、鉴权、超时和错误返回。
- 验收端点健康与修订检查、调用日志、权限隔离、未发布版本不可访问、原始输入不落库；文件输入尚未开放，不以卡片能显示作为完成标准。

### P1：完善市场和体验

- 增加示例输入、文件/媒体输入、结果下载和异步任务状态；分类筛选与搜索已在首期目录提供。
- 完善应用版本切换、下架、端点健康状态和 API 调用示例的可用性与文档覆盖；基础操作已在首期页面提供。
- 在首期调用记录上建立配额、限流和聚合错误统计。

### P2：开放应用接入

- 开放开发者自助接入、应用清单校验工具和最小 Python 调用 SDK。
- 增加发布审核、API 文档生成和更多经核验的应用包。

## 7. 首期明确不做

- 不追求复刻 400 个目录条目；先完成一个端到端样板，再按业务需求扩展。
- 不做一键 Notebook 开发、一键微调、一键部署、模型登记编排或 Label Studio/Pipeline 算子集成。
- 不自行重写 Kubernetes 调度、Notebook、Pipeline 或推理服务；AIHub 只调用已配置的运行端点。
- 不默认下载或分发第三方权重；每个模型先核对来源、使用许可和存储方式。
- 不建设商业售卖与计费流程；首期只有平台管理员管理权限和项目成员浏览权限，资源配额在 P1 加入。
